# TMDB 미러 배치 복구 분석 및 작업 계획 — 2026-11-19

## 판단 근거와 아직 확인되지 않은 것

- 8월 18일 Bulk Crawl은 큐 조회에서 Supabase `exceed_db_size_quota`로 실패했다. TMDB 호출 실패가 직접 원인은 아니다.
- 11월 19일 점검에서 로컬 설정의 기본 DB는 423.8MB였고, 메타데이터 33,373건은 180일 기준, 제공처 113,666건은 30일 기준을 넘었다. 큐는 비어 있었다. 이 수치는 운영 배치의 실제 대상 DB 수치로 확정되지 않았다.
- 기본 DB에는 `public.db_size_bytes()`가 없다. 현재 가드는 RPC 실패 시 `ok`로 진행한다.
- TMDB 정기 워크플로는 수동 비활성화돼 있다. 로컬 사고 대응 코드 4커밋은 원격 `main`에 없으므로, 현재 워크플로가 실행되면 원격의 옛 코드로 동작한다.
- GitHub 인증 토큰이 유효하지 않고 Vercel CLI도 인증되지 않아 Actions secrets와 배포 환경 변수의 설정 여부 및 대상 프로젝트를 확인하지 못했다.

## 원인과 재발 경로

1. 기존에는 미러 데이터가 사용자 DB에 함께 쌓여 500MB 한도를 넘었다. DB 용량에 맞춘 신규 유입과 방출 정책이 없었다.
2. 로컬의 가드와 미러 분리 코드는 원격 `main`에 없다. Vercel의 실제 배포 커밋은 미확인이다. 더구나 현재 가드는 RPC 누락·네트워크 오류에서 통과하고, 배치 시작 때 한 번만 검사한다.
3. Bulk Crawl 큐에는 신규 수집과 갱신이 섞일 수 있다. 코드는 420MB 이상에서 큐 전체를 갱신분으로 가정해 계속 소비하므로, 기존 신규 항목이 남아 있으면 용량이 더 늘 수 있다.
4. 배치 스크립트는 미러 URL과 키를 각각 독립적으로 기본 DB 값으로 대체한다. 한쪽만 설정되면 잘못 짝지어진 자격 정보로 요청할 수 있다. 웹 서버는 둘 중 하나가 없으면 기본 DB로 돌아간다. 잘못된 환경 설정을 조기에 실패시키는 검증이 필요하다.
5. 제공처 갱신도 detail·credits·providers를 모두 다시 받는다. 113,666건을 한꺼번에 처리하면 요청량과 DB 쓰기량이 크다. 현재 갱신 큐의 priority는 신규 큐와 같은 0이다. 재개 시 갱신이 자동으로 먼저 처리된다는 보장이 없다.

## 권장 복구 순서

### 1. 운영 대상과 용량 확정 — 읽기 전용

- GitHub와 Vercel 인증을 복구한 뒤, Production/Preview와 Actions의 Supabase 변수 **설정 여부 및 프로젝트 참조만** 비교한다. 비밀값은 기록하지 않는다.
- 기본 DB와 미러 DB 각각에서 전체 크기, 주요 테이블·인덱스 크기, 행 수, stale 건수, 큐 길이, `db_size_bytes()` 실행 가능 여부를 측정한다. 별도 미러가 존재하는지도 확인한다.
- 운영 워크플로가 실행할 커밋과 Vercel 배포 커밋을 기록한다. 각 DB의 Free/유료 플랜 및 실제 할당량을 확인한다.
- **진행 조건:** 읽기 경로와 쓰기 배치의 대상이 모두 확정되고, 복구 전 기준 수치가 남아 있어야 한다.

### 2. 안전 장치 수정과 검증 — 로컬 코드

- 가드 조회 실패를 성공으로 처리하지 않는다. 신규 유입은 실패로 종료하고, 갱신도 크기를 모르면 작업을 시작하지 않도록 한다. 가드 RPC의 반환형·권한·임계값 설정도 검증한다.
- 배치 진행 중 작은 쓰기 묶음마다 크기를 다시 확인한다. 중단 임계에 닿으면 다음 쓰기를 중단하고, 재실행 시 이미 성공한 작업을 안전하게 이어받도록 한다.
- 큐 항목에 `ingest`/`refresh` 의도를 보존하거나, 소비 시 메타데이터 존재 여부를 확인한다. 420MB 이상에서는 신규 수집을 확실히 건너뛰고 갱신만 처리한다. 갱신 우선순위도 명시한다.
- 미러 URL·키는 둘 다 설정되거나 둘 다 없어야 하며, 운영에서는 둘 다 필수로 강제한다. 배치 시작 로그에는 비밀값 없이 선택된 대상 역할만 출력한다.
- 작은 배치, 가드 실패, 420MB/460MB 경계, 혼합 큐, 재실행, 부분 실패를 검증한다. 실패 항목을 조용히 삭제하는 큐 처리도 재시도 가능하게 고친다.
- **진행 조건:** 단위·통합 검사와 실제 대상에 대한 읽기 전용 사전 점검이 통과해야 한다.

### 3. 저장 공간 확보와 미러 전환

- 사용자 DB와 미러 DB 분리는 장애 범위를 줄이지만 무료 용량 증가책으로 가정하지 않는다. Supabase의 현재 문서상 402 제한은 조직 내 DB 크기 합계와 청구 기간 평균에 근거한다. 미러 약 400MB를 별도 프로젝트에 복사하기 전에 조직 사용량과 대상 DB 예상 크기, 장기 보유 정책을 계산한다.
- 오래된 저가치 작품의 방출 기준, catalog와 metadata의 일관성, 임베딩 보관 범위를 정한다. 필요하면 더 큰 용량의 플랜을 선택한다. 플랜 변경만으로 신규 유입 무한 증가 문제는 해결되지 않는다.
- 스키마·RPC 적용 후 작은 단위로 이전하고 행 수, 주요 필드, 임베딩 수, 대표 조회 결과를 대조한다. 웹 읽기 경로와 Actions 쓰기 경로를 같은 미러로 전환한 후 관측한다.
- 이전 DB의 미러 테이블 삭제는 전환 검증과 복구 경로 확보 뒤 별도 작업으로 수행한다.
- **진행 조건:** 실제 쓰기 대상의 가드가 동작하고, 갱신으로 크기가 커져도 임계값까지 충분한 공간이 있어야 한다.

### 4. 제한적 재개와 backlog 처리

- 먼저 신규 유입 작업을 끈 채 제공처/메타데이터 갱신 후보를 작은 배치로 큐에 넣고 Bulk Crawl을 수동으로 소량 실행한다. 한 실행마다 DB 크기, API 오류율, 성공·실패·큐 건수, stale 감소량을 기록한다.
- 성공이 반복되면 배치 크기와 실행 횟수를 단계적으로 올린다. 30일 제공처 갱신 backlog 113,666건을 기본 1,000건/일 적재만으로 처리하면 최소 약 114일이므로, 처리량 목표를 별도로 정한다. 실제 대상 수치는 1단계에서 다시 잰다.
- backlog가 안정적으로 줄고 용량 추세가 관리될 때 정기 갱신을 켠다. 신규 catalog 유입은 방출 정책과 여유 용량이 확인된 후 마지막에 켠다. Initial Crawl은 재개 대상에서 제외한다.
- **중단 조건:** 가드 실패, 대상 불일치, 예상보다 빠른 크기 증가, 연속 API 실패, 큐의 비정상 증가가 발생하면 해당 배치를 중지하고 원인을 확인한다.

## 구독료 없이 운영하기 위한 로컬 중심 대안

DB가 계속 커져야 하는 것은 아니다. `tmdb_metadata`는 (tmdb_id, media_type) 키로 upsert하므로 기존 행을 갱신할 때 행 수가 무한히 늘지는 않는다. 현재는 신규 유입 상한만 있고, 오래되거나 가치가 낮은 작품을 방출하는 정책이 없어 총량이 증가한다. `tmdb_provider_snapshots`에는 7일 이전 데이터를 지우는 코드가 이미 있다.

권장하는 구조는 **로컬에서 수집·갱신하고, 온라인 DB에는 서비스가 읽는 제한된 작품 집합만 유지**하는 것이다.

1. 로컬 Postgres + pgvector에 전체 작업용 미러와 큐를 두고, 배치는 로컬에서 실행한다. 로컬 머신이 꺼져 있으면 갱신이 지연돼도 웹 서비스의 DB 조회는 계속 가능하다.
2. 실제 추천/장르/관련 작품의 조회량과 미러 적중률로 온라인 보유 작품을 정한다. 인기·KR OTT 가용 작품과 최근 사용 작품부터 시작하고, 온라인 DB는 측정한 크기 상한과 여유 공간을 유지한다.
3. 로컬에서 필요한 행만 온라인 DB에 작은 단위로 동기화한다. 신규 행을 올릴 때는 보유 한도에 맞춰 낮은 가치의 행을 방출하고, 두 테이블 및 임베딩 인덱스의 일관성을 검사한다. 누락 작품은 기존 TMDB 직접 조회 경로를 활용하되 요청량과 지연을 계측한다.
4. 온라인 서비스가 로컬 DB를 직접 조회하도록 연결하는 것은 별도 문제다. 현재 Vercel 서버 경로는 `supabaseMirror()`와 pgvector RPC를 사용한다. 집 PC를 실시간 데이터 서버로 쓰려면 외부 연결·가동률·보안·백업을 직접 운영해야 한다. 우선은 로컬 배치와 온라인 소형 읽기 DB를 분리한다.

로컬 검증에는 Supabase CLI 개발 스택을 쓸 수 있지만 공개 서비스로 노출하지 않는다. 실제 상시 자체 호스팅이 필요하면 Supabase 공식 Docker 배포 또는 필요한 구성 요소인 Postgres/pgvector/PostgREST만 별도로 운영한다. 참고: [로컬 개발](https://supabase.com/docs/guides/local-development), [자체 호스팅](https://supabase.com/docs/guides/self-hosting).

## 사용자 증가에 대비한 확장 경로

- 작품 미러는 여러 사용자가 공유하므로 사용자 수에 비례해 행 수가 늘 필요가 없다. 보유 작품 수·임베딩 크기를 고정하고 적중률을 측정한다. 사용자별 `profiles`·`saved_items`·`watch_reports`는 별도로 증가하므로 크기와 쿼리 비용을 따로 추적한다.
- 첫 단계에서는 공개 장르·작품 조회에 짧은 CDN 캐시를 적용하고, 개인화 추천·인증 응답은 공개 캐시하지 않는다. 동일한 읽기가 온라인 DB에 반복되는 비율을 낮춘다.
- 최소 지표는 일별 활성 사용자, 엔드포인트별 요청 수와 p95 응답 시간, DB/API 오류율, 미러 적중률과 TMDB 직접 조회 비율, DB 크기·egress, 로컬 동기화 지연, 사용자 데이터 크기다. 사용자 수 자체보다 이 지표의 한계 접근을 전환 기준으로 쓴다.
- 추천 API는 요청마다 OpenAI를 호출할 수 있으므로 사용자 증가 시 DB보다 API 비용이 먼저 문제가 될 수 있다. 현재 제한은 IP당 분당 60회이며 Redis 설정이 없거나 실패하면 인스턴스별 메모리 제한으로 돌아간다. 공개 서비스 전에는 사용자·일별 예산, 전역 지출 상한, 비정상 요청 차단 및 무료 사용량 정책을 설계한다.
- 읽기 지연·요청량이 문제라면 캐시와 쿼리·인덱스를 먼저 최적화한다. 온라인 DB 크기가 문제라면 보유 집합·임베딩 범위·방출 정책을 조정한다. 로컬 배치 처리 지연이 문제라면 배치 실행 머신이나 실행 주기만 확장한다. 서로 다른 병목을 한 번에 유료 DB로 해결하려 하지 않는다.
- 무료 한도를 지속적으로 넘거나 p95 지연·오류가 목표를 넘어서면 온라인 읽기 DB만 더 큰 관리형 서비스로 이전한다. 로컬 수집기와 동기화 계약을 분리해 두면 수집 파이프라인은 유지할 수 있다. 실제 전환 전에는 비용 상한과 복구 경로를 확인한다.

참고: [Vercel Cache-Control](https://vercel.com/docs/caching/cache-control-headers), [Supabase egress](https://supabase.com/docs/guides/platform/manage-your-usage/egress).

현재 단계에서 권장하는 다음 작업은 **1단계 운영 대상 확인과 2단계 안전 장치 구현**이다. 정기 워크플로 재개, DB 변경, 배포는 아직 진행하지 않는다.

용량 기준 참고: [Supabase 요금표](https://supabase.com/pricing), [Database size 설명](https://supabase.com/docs/guides/platform/database-size). Free 플랜의 500MB 데이터베이스 크기와 디스크 사용량 한도는 서로 다른 지표다.
