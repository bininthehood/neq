# 로컬 미러 재개 점검 — 2026-11-20

## 현재 위치

- 로컬 Supabase 미러에 `tmdb_catalog`와 `tmdb_metadata` 각 113,666건을 복사했다. 첫 백업은 `~/Documents/neko-backups`에 있고, 기본 백업 경로를 Workspace 볼륨의 `../neko-backups`로 변경했다. 아카이브 목록은 `pg_restore -l`로 검사하며 실제 복원 시험은 아직 하지 않았다.
- 로컬 DB는 약 572.4MB다. `tmdb_metadata`가 약 540MB이며 로컬 IVFFlat 인덱스만 약 204MB다. 로컬 미러는 loopback Docker 네트워크에서 실행된다.
- Docker 컨텍스트는 Colima이고 `~/.colima`가 `/Volumes/Workspace/Projects/.kwp2-colima`를 가리킨다. 따라서 Docker DB 데이터도 Workspace 볼륨에 있다. 시스템 디스크의 여유는 약 16GB이며 첫 백업만 그 디스크에 있다. 로컬 배치와 백업의 여유 공간은 Workspace 볼륨을 기준으로 감시한다.
- 기본 설정의 호스팅 DB는 읽기 전용 SQL로 423.8MB를 확인했다. `tmdb_metadata` 약 399MB는 heap 109MB, 인덱스 70MB, TOAST 등 221MB로 구성된다. 온라인에는 로컬의 204MB IVFFlat 인덱스가 없다.
- GitHub CLI 토큰은 만료됐고 Vercel CLI는 미인증이다. 따라서 이 호스팅 DB가 실제 Production 대상인지 아직 확정되지 않았다. 로컬 `main`은 원격보다 4커밋 앞서고, 이번 작업은 미커밋 상태다.

## 축소 미리보기와 용량 판단

- 추천 SQL은 `providers IS NOT NULL`인 작품을 후보로 사용한다. 구독형만 필수로 보존하면 나머지 제공처 작품 5,856건 중 약 5,000건을 잃는다. 미리보기 기준을 모든 제공처 작품으로 수정했다.
- 수정된 30,000건 미리보기는 제공처 작품 25,924건 전부를 포함한다. 현재 호스팅 DB와 비교하면 신규 업로드 0건, 방출 후보 83,666건이다. 이는 **DB 쓰기 없는 후보 계산**이다.
- 이 30,000건에는 임베딩 25,936건이 포함된다. 로컬에서 측정한 선택 집합의 메타데이터 논리 크기는 약 189.5MB이고 그중 벡터가 약 152.1MB다. 전체 벡터 논리 크기 152.7MB와 거의 같다. 따라서 행을 74% 줄여도 벡터 용량은 거의 줄지 않는다.
- 제공처 작품 중 인기 상위 5,000건만 벡터를 남기는 가정에서는 벡터 논리 크기가 약 29.3MB다. 이는 저장 공간 절감 가능성의 추정치이며, 벡터 검색·DPP 다양성·즐겨찾기 취향 벡터의 적중률을 낮출 수 있다. 실제 배포 전 추천 품질과 적중률을 측정해야 한다.
- PostgreSQL의 `DELETE`나 벡터 값을 `NULL`로 바꾸는 것만으로 파일 크기가 즉시 줄지는 않는다. 안전한 공간 회수 또는 새 compact DB로 이전하는 계획 없이 현재 423.8MB의 DB에 대량 쓰기를 하면 무료 한도에 다시 접근할 수 있다.

## 로컬 갱신 시험

- 오래된 순서로 뽑은 비제공처 10건은 TMDB 상세 조회에서 모두 404였다. 알려진 TMDB 작품은 같은 API 키로 200을 반환했다.
- `PROVIDERS_ONLY=true`를 추가해 제공처 작품 10건을 로컬 큐에 넣고 갱신했다. 6건 성공, 4건 404였다. 로컬 큐에는 현재 404 실패 14건이 한 번씩 기록되어 있다.
- (2026-11-23) 제공처 작품 200건을 로컬에서 갱신했다. 199건 성공, 404 1건(제거), 소요 35초(약 5.7건/초, `TMDB_RATE_LIMIT_RPS=30` 기본값). 앞선 10건 시험의 404 비율 40%는 오래된 순 표본의 편향이었고, 제공처 작품의 404 비율은 약 0.5%다.
- **제공처 재발견 정책(제안):** 로컬이 전체 113k건을 보유하고, 로컬에서 `refresh-providers`를 `PROVIDERS_ONLY` 없이 30일 주기로 돌린다. 하루 약 3,800건, 측정 처리량 기준 약 11분이다. 제공처가 새로 생긴 작품은 로컬 serving-set 계산에 자동으로 들어가 다음 온라인 동기화 때 올라가고, 제공처가 사라진 작품은 방출 후보가 된다. 온라인 미러는 재발견을 위해 비제공처 작품을 보유할 필요가 없다.
- 전체 갱신 전에 영구 404 작품의 tombstone/방출 규칙을 설계하고, 제공처가 바뀐 작품을 어떻게 재발견할지 정해야 한다. 지금의 제공처 집합은 30일 기준으로 모두 오래됐다.
